# Упрощенная CRM-система для ШИФТ ЛАБ

## Описание проекта

Это упрощенная CRM-система, разработанная для управления информацией о продавцах и их транзакциях. Система предоставляет RESTful API для выполнения CRUD-операций (создание, чтение, обновление, удаление) с данными, а также включает аналитические функции для обработки и анализа данных о продажах.

Проект реализован на языке Java с использованием фреймворка Spring Boot. В качестве базы данных используется PostgreSQL. Система поддерживает принципы сохранения историчности данных через "мягкое удаление" (soft delete).

## Основные возможности

- **Управление продавцами**:
    - Создание, обновление и "мягкое" удаление продавцов.
    - Получение списка всех продавцов (как активных, так и всех, включая удаленных).
    - Получение подробной информации о конкретном продавце.
- **Управление транзакциями**:
    - Регистрация новых транзакций с привязкой к продавцу.
    - "Мягкое" удаление транзакций.
    - Получение списка всех транзакций.
    - Получение информации о конкретной транзакции.
    - Получение всех транзакций конкретного продавца.
- **Аналитика**:
    - Определение самого продуктивного продавца за указанный период (день, месяц, квартал, год). Продуктивность определяется по максимальной сумме всех транзакций.
    - Получение списка продавцов, у которых общая сумма транзакций за выбранный период меньше заданного значения.
- **Документация API**:
    - Интегрированная Swagger UI для удобного просмотра и тестирования API.

## Используемые технологии

- **Язык программирования**: Java 25
- **Фреймворк**: Spring Boot 3.5.6
- **База данных**: PostgreSQL (основная), H2 (для тестирования)
- **ORM**: Spring Data JPA / Hibernate
- **Сборщик проекта**: Gradle
- **Управление зависимостями**:
    - `spring-boot-starter-web`: для создания REST-контроллеров.
    - `spring-boot-starter-data-jpa`: для работы с базой данных.
    - `spring-boot-starter-validation`: для валидации входящих данных.
    - `postgresql`: драйвер для PostgreSQL.
    - `lombok`: для сокращения шаблонного кода.
    - `modelmapper`: для удобного маппинга между DTO и сущностями.
    - `springdoc-openapi-starter-webmvc-ui`: для автоматической генерации документации Swagger.
- **Контейнеризация**: Docker, Docker Compose
- **Тестирование**: JUnit 5, Mockito, Testcontainers

## Архитектура проекта

Проект имеет многослойную архитектуру для лучшего разделения ответственности:

- **`controllers`**: Слой для обработки входящих HTTP-запросов и вызова соответствующей бизнес-логики.
- **`services`**: Слой бизнес-логики, инкапсулирующий основные операции приложения.
- **`repositories`**: Слой доступа к данным, использующий Spring Data JPA для взаимодействия с базой данных.
- **`entities`**: Определения JPA-сущностей, которые отображаются на таблицы базы данных (`SellerEntity`, `TransactionEntity`).
- **`data/dto`**: Объекты для передачи данных (Data Transfer Objects) между слоями, что позволяет отделить API от внутренней структуры базы данных.
- **`mappers`**: Утилиты для преобразования между DTO и сущностями.
- **`exceptions`**: Классы для обработки исключительных ситуаций и централизованный обработчик ошибок `GlobalExceptionHandler`.
- **`config`**: Конфигурационные классы для настройки бинов, таких как ModelMapper и OpenAPI.

## Инструкции по сборке и запуску

### Предварительные требования

- JDK 25 или выше
- Docker и Docker Compose

### Запуск с помощью Docker Compose (Рекомендуемый способ)

1.  **Создайте файл `.env`** в корневой директории проекта и укажите в нем учетные данные для базы данных:
    ```env
    POSTGRES_DB=crmdb
    POSTGRES_USER=crmuser
    POSTGRES_PASSWORD=crmpassword
    ```

2.  **Соберите и запустите приложение** с помощью Docker Compose. Вы можете выбрать один из профилей: `jvm` (стандартная сборка) или `native` (сборка в GraalVM Native Image).

    - **Для запуска JVM-версии:**
      ```bash
      docker-compose --profile jvm up --build
      ```
    - **Для запуска Native-версии (требует больше времени на сборку):**
      ```bash
      docker-compose --profile native up --build
      ```

3.  После успешного запуска приложение будет доступно по адресу: `http://localhost:8085`.

4.  **Документация API (Swagger UI)** будет доступна по адресу: `http://localhost:8085/swagger-ui.html`.

## Тестирование

Проект содержит юнит-тесты для сервисного слоя и интеграционные тесты (Testcontainers) для
взаимодействия с реальными PostgreSQL и Redis.

### Юнит-тесты (быстрые, без Docker)

```bash
./gradlew test
```

Отчет: `build/reports/tests/test/index.html`.

### Интеграционные тесты (Testcontainers)

Интеграционные тесты находятся в отдельном source set `src/integrationTest`. При запуске они
поднимают эфемерные контейнеры **PostgreSQL 16** и **Redis 7** через Testcontainers, а затем
проверяют сквозное взаимодействие: персистентность в PostgreSQL, кэширование продавцов в Redis,
инвалидацию кэша при обновлении/удалении и аналитику по транзакциям.

Запуск (требуется работающий Docker):

```bash
./gradlew integrationTest
```

Отчет: `build/reports/tests/integrationTest/index.html`.

### Параллельное выполнение интеграционных тестов

Количество JVM-форков задаётся свойством `integrationForks` (по умолчанию `1` — последовательно):

```bash
# последовательно
./gradlew integrationTest -PintegrationForks=1

# параллельно (4 форка)
./gradlew integrationTest -PintegrationForks=4
```

Замер на локальной машине (2 тестовых класса, 7 тестов, каждый поднимает свой набор контейнеров):

| Режим | Время (wall-clock) |
|-------|--------------------|
| Последовательно (`integrationForks=1`) | ~7.2 c |
| Параллельно (`integrationForks=4`)      | ~6.5 c |

Параллельный запуск запускает контейнеры и контексты тестовых классов одновременно, что сокращает
общее время. Полный запуск всех тестов (юнит + интеграция) — `./gradlew build`.

> **Примечание для окружений с нестандартным Docker (Colima/Docker Machine).**
> В `build.gradle` для задачи `integrationTest` включена переопределяемая стратегия подключения
> к Docker (`EnvironmentAndSystemPropertyClientProviderStrategy`), которая читает `DOCKER_HOST`
> из окружения, и фиксированная версия Docker API `1.44`. В CI (дефолтный docker-сокет) эти
> настройки безвредны и откатываются на стандартное поведение.

## CI/CD и GitOps

Пайплайн описан в `.github/workflows/ci.yml` (GitHub Actions). Джобы и зависимости:

```
test  ──►  integration-tests  ──►  docker (build + publish)  ──►  promote-staging  ──►  update-gitops
         (Testcontainers,                  сборка и публикация           копия манифеста          GitOps:
          parallel)                        ТОЛЬКО после тестов           в staging без rebuild    коммит тега
```

- **`test`** — юнит-тесты.
- **`integration-tests`** (`needs: test`) — интеграционные тесты Testcontainers, запускаются
  параллельно (`-PintegrationForks=4`).
- **`docker`** (`needs: [test, integration-tests]`) — сборка, сканирование Trivy и **публикация**
  образа в GHCR происходят только после успешного прохождения обеих стадий тестов.
- **`promote-staging`** (`needs: docker`, только для `master`) — продвигает проверенный образ
  в `:staging` через `docker buildx imagetools create`, т.е. **без повторной сборки** (копируется
  манифест в реестре).
- **`update-gitops`** (`needs: promote-staging`) — автоматически обновляет тег образа
  в манифесте `k8s/crm-deployment.yaml` и коммитит его в ветку `gitops`. Это и есть механика
  GitOps: Git является единственным источником истины, а внешний контроллер (Argo CD / Flux)
  синхронизирует состояние кластера с этой веткой. Отдельная ветка `gitops` не запускает
  пайплайн повторно и не создаёт циклов.

Kubernetes-манифесты: `k8s/crm-deployment.yaml`, `k8s/crm-service.yaml`.

## Примеры использования API (Эндпоинты)

### Продавцы (`/api/sellers`)

- `GET /`: Получить список всех активных продавцов.
- `GET /all-with-deleted`: Получить список всех продавцов, включая удаленных.
- `GET /{id}`: Получить информацию о продавце по его ID.
- `POST /`: Создать нового продавца.
    - **Тело запроса:**
      ```json
      {
        "name": "Иванов Иван Иванович",
        "contactInfo": "ivanov@example.com, +79990001122"
      }
      ```
- `PUT /{id}`: Обновить информацию о продавце.
    - **Тело запроса:**
      ```json
      {
        "name": "Иванов Иван Петрович",
        "contactInfo": "new-email@example.com"
      }
      ```
- `DELETE /{id}`: "Мягко" удалить продавца.
- `GET /{sellerId}/transactions`: Получить все транзакции для конкретного продавца.

### Транзакции (`/api/transactions`)

- `GET /`: Получить список всех активных транзакций.
- `GET /all-with-deleted`: Получить список всех транзакций, включая удаленные.
- `GET /{id}`: Получить информацию о транзакции по ID.
- `POST /`: Создать новую транзакцию.
    - **Тело запроса:**
      ```json
      {
        "sellerId": 1,
        "amount": 1500.50,
        "paymentType": "CARD"
      }
      ```
- `DELETE /{id}`: "Мягко" удалить транзакцию.

### Аналитика (`/api/sellers/analytics`)

- `GET /most-productive`: Получить самого продуктивного продавца за период.
    - **Параметры запроса:**
        - `start`: Дата и время начала периода (формат ISO `YYYY-MM-DDTHH:MM:SS`).
        - `end`: Дата и время окончания периода (формат ISO `YYYY-MM-DDTHH:MM:SS`).
    - **Пример:** `/api/sellers/analytics/most-productive?start=2024-01-01T00:00:00&end=2024-03-31T23:59:59`

- `GET /below-amount`: Получить продавцов, сумма транзакций которых за период меньше указанной.
    - **Параметры запроса:**
        - `start`: Дата и время начала периода.
        - `end`: Дата и время окончания периода.
        - `amount`: Максимальная общая сумма транзакций.
    - **Пример:** `/api/sellers/analytics/below-amount?start=2024-01-01T00:00:00&end=2024-01-31T23:59:59&amount=5000`
